> 导读：本次 v1.20.0 让桌面 GUI 客户端与 Reflex Web 版共享同一套问题反馈体系——桌面端通过 HTTP multipart 提交到 Web 服务端 API，落同一个 SQLite 库，管理员在一处处理全部反馈。本文重点拆解三个实现细节：SQLModel 旧库的幂等加列迁移、PySide6 QtNetwork 的 multipart 异步上传、以及 Reflex 框架跨 State 通信的三个坑。

## 一、版本亮点

### 1. 桌面客户端内置问题反馈

帮助菜单新增「问题反馈」入口，弹出的对话框支持问题类型 / 涉及协议下拉、问题描述（实时字数统计）、联系方式、最多 3 张截图。对话框还会自动收集运行环境信息（软件版本、操作系统、Python 版本、当前选中的协议），随反馈一起提交——排查问题时不用再来回问"你用的什么版本"。

### 2. Web 服务端开放反馈 API

Web 端新增两个接口：

- `POST /api/feedback`：multipart 表单提交（字段 + 截图），带滑动窗口频率限制（60 秒内同一 IP 最多 5 条）；
- `GET /api/feedback/config`：下发字段约束（类型白名单、长度上限、截图张数/大小限制），客户端启动时拉取，避免两端规则不一致。

### 3. 一个数据库，两个入口

桌面端与网页表单提交的反馈写入**同一个 SQLite 数据库**，记录带 `source` 字段（`web` / `gui`）区分来源。Web 管理端列表中桌面端来源的记录会显示"桌面端"徽章，点开详情可看到客户端环境信息。管理员在 Web 端统一做状态流转（待处理 → 已确认/已修复/已忽略）和删除，无需两处登录。

## 二、技术点深挖 1：SQLModel 旧库的幂等加列迁移

### 背景与问题

v1.19.0 的反馈表只有 8 个字段；v1.20.0 要给 `FeedbackItem` 增加 `source` 和 `sys_info` 两列。问题在于：`SQLModel.metadata.create_all()` 只会**创建缺失的表**，对**已存在的表不会补列**。已部署环境的旧 `feedback.db` 直接跑新版，一执行带新列的查询就会 `OperationalError: no such column`。

完整的 Alembic 迁移链对这个小工具来说太重了——我们只需要"旧库首次打开时自动补列"这一个能力。

### 实现方案

在 `FeedbackStore` 初始化（建库 + `create_all`）之后，跑一个轻量迁移：读 `PRAGMA table_info` 拿到现有列集合，缺哪列补哪列：

```python
@staticmethod
def _migrate_source_column(engine):
    """旧库轻量迁移：缺列则 ALTER TABLE 补列（create_all 不会给已存在表加列）。"""
    # SQLite ADD COLUMN 必须带默认值
    wanted = {
        "source": "VARCHAR DEFAULT 'web'",
        "sys_info": "VARCHAR DEFAULT ''",
    }
    with engine.connect() as conn:
        rows = conn.exec_driver_sql("PRAGMA table_info(feedbackitem)").fetchall()
        cols = {r[1] for r in rows}
        for name, decl in wanted.items():
            if name not in cols:
                conn.exec_driver_sql(
                    f"ALTER TABLE feedbackitem ADD COLUMN {name} {decl}"
                )
        conn.commit()
```

几个设计取舍：

- **幂等**：每次启动都跑，靠"列名是否在集合里"判断，重复执行无副作用；
- **历史数据语义正确**：`source` 默认 `'web'`——v1.19.0 时代的存量记录确实全部来自网页；
- **`exec_driver_sql` 而非 ORM**：DDL 语句本来就不该过 ORM 层，驱动层直通最简单，也绕开了 SQLModel 的类型检查。

## 三、技术点深挖 2：PySide6 桌面端的 multipart 异步上传

### 背景与问题

桌面端提交反馈要带截图（单张可达 5MB），必须走 `multipart/form-data`；同时 GUI 线程绝不能被网络 IO 阻塞。方案上没有引入 `requests`——PySide6 自带的 **QtNetwork** 就能完整覆盖，零额外依赖（这对打包体积和依赖管理都是收益）。

### 实现方案

核心是 `QNetworkAccessManager` + `QHttpMultiPart`：

```python
multi = QHttpMultiPart(QHttpMultiPart.FormDataType)

# 文本字段
part = QHttpPart()
part.setHeader(QNetworkRequest.KnownHeaders.ContentDispositionHeader,
               'form-data; name="description"')
part.setBody(description.encode("utf-8"))
multi.append(part)

# 截图文件（name 固定，filename 带原始扩展名供服务端校验）
file_part = QHttpPart()
file_part.setHeader(QNetworkRequest.KnownHeaders.ContentDispositionHeader,
                    f'form-data; name="screenshots"; filename="{fname}"')
file_part.setHeader(QNetworkRequest.KnownHeaders.ContentTypeHeader, "image/png")
file_part.setBody(image_bytes)
multi.append(file_part)

req = QNetworkRequest(QUrl(server_url + "/api/feedback"))
req.setTransferTimeout(20000)  # 20 秒超时
reply = self._nam.post(req, multi)   # 异步发出，立即返回
multi.setParent(reply)               # 生命周期挂到 reply 上，防止提前析构
```

两个容易踩的细节：

1. **中文必须显式 UTF-8**：`setBody` 接收 bytes，直接 `setBody("中文".encode("utf-8"))`，服务端按 UTF-8 解；若依赖 Qt 默认转码，跨机器 locale 不同时会乱码。
2. **multipart 对象生命周期**：`QHttpMultiPart` 在 `post()` 返回后必须 `setParent(reply)`，否则 Python 侧引用一释放，Qt C++ 对象跟着析构，请求发出去是空的——表现为服务端收到"没有 boundary 的空请求"，非常难查。

提交结果通过 `reply.finished` 信号回到 GUI 线程，解析 JSON 后更新对话框状态条；超时、非 200、JSON 解析失败分别给不同的用户提示。全程无阻塞、无手写线程。

### 服务端怎么接

生产模式（ASGI 中间件）拿不到框架的 form 解析，需要**手工解析 multipart**：按 `boundary` 切分 body，每个 part 从 `Content-Disposition` 里取 `name`/`filename`，头部与正文之间用 `\r\n\r\n` 分隔，正文按二进制原样保留（截图字节不能被任何文本解码污染）。这段解析器是纯函数，用"文本字段（含中文多行）+ 二进制 PNG 往返"的单测锁住行为。

业务逻辑则收敛到一个纯函数 `submit_from_api(fields, files) -> (ok, id_or_error, http_status)`：字段白名单校验、长度校验、截图扩展名 + 文件头魔数 + 大小三重校验、文件名服务端重生成（用户上传的原始文件名**完全不参与**落盘路径，防路径穿越）、部分失败时回滚已落盘文件。开发模式的 Starlette 路由和生产模式的手工解析中间件共用这同一个函数——两条路径行为完全一致，单测只需覆盖一处。

## 四、技术点深挖 3：Reflex 跨 State 通信的三个坑

Web 管理端的反馈列表挂在主 State 上，而反馈提交逻辑在独立的 `FeedbackState`——这个拆分让我把 Reflex（0.9.8）跨 State 的坑集齐了：

**坑 1：前端 Var 不能跨 State 引用。** 组件里写 `other_state.var` 会直接编译错误。解法是让子 State 继承主 State（`class FeedbackState(State)`），继承链上的父类变量前后端都可见。

**坑 2：后端 handler 的 `self` 也只看得到自己类链上的变量。** 就算前端躲开了，`FeedbackState` 的删除事件里访问主 State 的 `admin_logged_in` 登录标志，运行时照样 `AttributeError`。同样靠继承解决——这也是权限校验（"管理员才能删除"）能复用主 State 登录态的前提。

**坑 3：A State 的事件里直接改 B State 的变量，前端收不到。** Reflex 的状态 delta 只随**各自 State 自己的事件**推送。最初"点击反馈 Tab"时在主 State 的 `set_tab` 里顺手调了 `FeedbackState` 的列表加载，后端确实查了库，但 `fa_items` 的 delta 没跟着主 State 事件下发，前端列表永远空白。正确姿势是用**事件链**：

```python
rx.el.button(
    "问题反馈",
    on_click=[
        lambda: State.set_tab("feedback"),   # 主 State：切 Tab
        FeedbackState.fa_load,               # FeedbackState：拉列表并推送自己的 delta
    ],
)
```

**坑 4（附赠）：受控弹窗关不掉。** `rx.dialog` 用 `open=State.bool_var` 受控时，内置的 `rx.dialog.close` 只发 Radix 内部关闭事件，**不会回写 State 的布尔值**——点关闭没反应。必须同时：关闭按钮显式绑 `on_click=关闭事件`，且 `dialog.root` 挂 `on_open_change=同步事件`（处理点遮罩、Esc 两条关闭路径）。

## 结语

这版的核心思路是"**一个数据源，多个入口**"：反馈无论从桌面还是网页来，都进同一个库、同一套状态流。实现上刻意把业务收敛到纯函数（校验、提交、迁移），让 dev/prod 两条路由、网页/桌面两个客户端共享同一份逻辑，测试也只需覆盖一处。下一篇打算聊聊虚拟表从站模拟器的组帧回读测试思路，欢迎在评论区留下你的反馈。
