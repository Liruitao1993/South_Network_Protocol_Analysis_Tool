# 南网协议解析工具 · 优化点梳理（2026-10-20，基于 v1.23.88）

> 依据：本地代码实测（116 个根模块 / 118,580 行 / 190 个测试文件 / 20 个标签页）、
> `AGENTS.md` 与 `main_gui.py:CHANGELOG` 的既有约定、以及当前发布产物（单文件 EXE 103 MB）。
> 每条都标了**证据**，避免「拍脑袋优化」。

## 0. 先看结论：最值得先做的 5 件事

| # | 事项 | 为什么现在做 | 预期收益 | 成本 |
|---|------|--------------|----------|------|
| 1 | 拆 `main_gui.py`（13,984 行） | 单文件承载 20 个标签页的创建/联动/主题/串口/升级/托盘，任何改动都在最大文件里做 | 后续每个需求的改动面与回归风险明显下降 | 中（2~3 天，可分 4 批） |
| 2 | 发布形态改「安装版 + 便携版」 | 103 MB 单文件每次启动要自解压；无代码签名会触发 SmartScreen | 冷启动更快、下载顾虑更少 | 小（已有 Inno Setup 脚本） |
| 3 | 把「生产测试架」升级成「测试流程」 | 现在只能发一条参数帧，产线真正要的是「一键跑完一组测试并判定 Pass/Fail」 | 从「调试工具」变成「产线工具」，是最大的差异化卖点 | 中 |
| 4 | CI 自动发版（GitHub Actions） | 现在靠人跑 `release_check`（约 3 分钟）+ 手工 PyInstaller + 手工传 Release | 发版从 30 分钟降到点一下，版本信息不会漂 | 中（半天） |
| 5 | 内置「一键诊断包」 | 远程支持时最耗时的是「让对方把配置/日志/环境发来」 | 支持成本下降，公众号读者也能自助排障 | 小（半天） |

## 1. 性能与体积

**证据**
- 源码态实测：`import main_gui` **1.41 s** + `MainWindow()` **1.35 s** ≈ **2.8 s**（离屏、SSD）。
- 冻结态单文件 103 MB，PyInstaller 每次启动先解包到临时目录，实际冷启动还要再加数秒。
- spec 明确不排除 `pandas/numpy/pyarrow`（导出用），这三者占了包体的大头。

**建议**
1. **延迟导入重依赖**：`pandas`、`openpyxl`、`crcmod`、`scapy`、`bleak`、`lupa` 都应「用到才 import」。
   现在 `main_gui` 顶层已经比较克制，建议用 `python -X importtime` 生成一次基线，按累计耗时排序逐个下沉。
2. **先画壳再初始化**：`MainWindow.__init__` 里创建 20 个标签页（多数是占位 + 懒加载，已经不错），
   可把「查询页/图表页/表格样式」再往后挪，先 `show()` 再 `QTimer.singleShot(0, ...)` 完成剩余初始化。
3. **发布两种形态**：
   - 安装版（`南网解析工具.iss` 已有）：`onedir` + Inno Setup，启动快、可增量更新；
   - 便携版 zip：解压即用，适合内网/无管理员权限的现场。
   单文件 EXE 保留为「应急版」即可。
4. **表格虚拟化**：批量解析若一次性把几万行塞进 `QTableWidget`，内存与插入耗时都会陡增。
   建议用 `QAbstractTableModel` + `QTableView`（或先给 1 万/5 万帧做一次压测，拿到数据再决定）。
5. **大日志**：串口工具已有节流与 5000 行上限，建议同样给「生产测试架」的接收日志加「高吞吐时按 100 ms 批量刷新」，
   现在是一帧一次 `insertText`（`_log`），10 kbps 以上会明显卡 UI。

## 2. 架构与可维护性

**证据**：`main_gui.py` 13,984 行；最大的解析器 `csg_new_gen_parser.py` 6,957 行；`AGENTS.md` §8 已积累 78 条「陷阱」。

**建议**
1. **按功能区拆 `main_gui`**（不必一次到位）：
   - `ui/main_window.py`（壳 + 布局）
   - `ui/serial_bar.py`（顶部串口配置）
   - `ui/tabs/*.py`（每个标签页的创建与信号接线）
   - `app/commands.py`（托盘/命令行/快捷键路由）
   拆分时保持「页面不 import main_gui」的既有约定，能力继续走注入。
2. **把「字段表驱动」推广开**：`production_testbench_core.FIELD_SPECS` 这种「一份表同时驱动界面/组帧/落盘」的模式，
   很适合 `dx` 类参数页（测试方案、预设命令、协议组帧的部分子页），能显著减少「界面改了、组帧没改」的漂移。
3. **静态检查基线**：`ruff`（已有部分注释风格）+ `mypy --ignore-missing-imports` 先只卡新增文件，
   避免一次性几千条报错。
4. **陷阱转测试**：§8 里每条陷阱都应该对应一条断言（现有测试已覆盖很多，建议做一次盘点，列出「有陷阱无测试」的清单）。
5. **依赖锁定**：根目录补 `requirements.txt`（锁定 PySide6/pyserial/crcmod/openpyxl 版本），
   避免用户 `pip install` 到不兼容版本（PySide6 6.x 小版本偶有 API 变化）。

## 4. 协议与测试能力

1. **桌面 15 协议 vs Web 12 协议**：Web 版缺协议 13（依瓦 645）/14（南网上行）的解析与组帧。
   推广时要么补齐，要么在首页显式标注「桌面端专属」，**避免用户按 Web 的能力预期下载桌面版**。
2. **协议 8 升级**：已支持逐包确认/重试/波特率提升，建议再加「断点续传（记住已确认块号）」与「失败原因码中文化」。
3. **生产测试架 → 测试流程**（最推荐的产品化方向）：
   - 多套参数模板（保存/切换/导入导出）；
   - 一页配置「发什么 → 等什么 → 判定规则」，一键跑完给出 Pass/Fail；
   - 结果落 CSV/Excel，直接对接产线 MES 或打印标签。
4. **Golden 用例继续扩**：厂商定制协议（依瓦、万胜、HDC）最容易在改公共代码时被误伤，
   建议每个协议固定 3~5 条现场实帧做「逐字节重建 + 校验通过」的回归。
5. **一致性对拍**：桌面与 Web 的解析结果已有 `test_web_gui_parity.py`，建议把「新增协议必须过对拍」写进 checklist。

## 5. 质量与发布

1. **测试分层**：190 个测试文件、全量约 3 分钟。建议分三档：
   - `smoke`（30 s，20 个关键用例）：提交前跑；
   - `core`（3 min，现状）：发版前跑；
   - `full`（含 GUI/Web）：CI 夜间跑。
2. **代码签名**：无签名 → 用户首次运行会被 SmartScreen 拦。短期在下载页给 SHA-256 与「如何校验」；
   中长期买 OV 证书（约千元/年）能显著提升下载转化。
3. **发版脚本化**：`bump 版本 → 改 CHANGELOG → --sync-iss → 构建 → 算 SHA256 → 传 Release → 更新 version.json`，
   建议做成一个 `tools/release.py`，并把 GitHub Actions 接上。
4. **反馈闭环**：已有反馈对话框 + feedback.db；建议加「问题分类/设备型号/协议」三个下拉，方便你在后台按类处理。

## 6. 针对「推广」的产品化补丁（做完再推，转化更高）

1. **下载页加 3 分钟上手 GIF/视频**：从「粘贴一帧」到「看到逐字段解析」。
2. **示例报文包**：每个协议 2~3 条脱敏实帧，一键载入，读者下载后 10 秒内能看到效果。
3. **版本亮点页**：把 CHANGELOG 里用户能感知的点（地址替换、升级判定、生产测试架）做成图文，发版即发公众号。
4. **内网离线包**：AGENTS 里已有 Reflex Web 的离线/内嵌部署方案，可打包成「一台机器就能当解析服务」的卖点。
5. **二维码/下载引导**：公众号后台回复关键词自动发下载链接（见 `推广/公众号/00-注册开通指引.md`）。
