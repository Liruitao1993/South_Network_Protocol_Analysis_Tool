# 产品级优化评估（2026-10-20，v1.23.88）

> 立场：按「要发给外部用户、装上就要能稳定跑」的标准评估，而不是「自己用着还行」。
> 所有数字都是**本机实测**（源码态、i7 级别 CPU / SSD / Windows 11），不是估算。
> 结论先行：**解析性能已经够用，短板在"产品化外壳"**——启动、更新兜底、配置写入、异常兜底、签名与可诊断性。
>
> **实施状态（2026-10-20，v1.23.89）**：P0-1（升级兜底）、P0-2（配置原子写）、P0-4（诊断包）**已完成**；
> P0-3（代码签名）需证书，短期以 SHA-256 公示为主。测试 `test/test_p0_hardening.py` 13 项已进发布门禁。
>
> **第二阶段（v1.23.90）**：P1 的「性能（拓扑页首开、测试架日志合并刷新）」「稳定性（崩溃兜底日志）」
> 「协议准确性（真实帧语料库 + 模糊测试，并修掉国网截断帧越界）」已完成；
> 剩余 P1（安装版/便携版双形态、增量更新、灰度通道、其它模块 JSON 原子写、表格虚拟化）属发布与批次改造。

## 二、P0：发布前必须补的 4 件事

### 1）自动升级没有「失败兜底」（最高风险）

**现状**（`auto_updater.py:528` 的 `UPDATE_BAT_TEMPLATE`）：

```
等待旧进程退出 → copy /y /b 新包 覆盖 旧包 → start 旧路径 → 删临时文件
```

问题：

- **覆盖前不备份**：复制到一半断电/被杀软锁文件/磁盘满，旧 exe 已被截断 → 用户手上没有可运行的程序。
- **覆盖后不校验**：没有比对覆盖后的文件大小/哈希。
- **启动失败不回落**：新版一启动就崩（缺 DLL、系统版本不兼容），没有任何机制退回旧版。
- **无健康检查**：新进程起来后 10 秒内崩溃，也当作升级成功。

**建议（一天内可完成）**：

1. `copy` 前把旧 exe 重命名为 `xxx.exe.bak`（同目录）；
2. 覆盖后校验大小 + SHA-256（已有 `sha256_of`）；
3. `start` 新 exe 后等待 15 秒，若进程不在或版本号没变 → 自动恢复 `.bak` 并重启；
4. 保留最近 1 个 `.bak`，在「关于」里给一个「回退到上一版」入口。

**验收**：手动破坏一次下载文件（截断 10%），升级流程必须自动回滚且能正常启动。

### 2）配置文件不是原子写

**现状**：`main_gui.py` 有 6 处 `open(config_path, "w") + json.dump`（8002 / 8606 / 11428 / 11571 / 13336 / 13432）。
写入过程中崩溃、断电、杀进程 → `config.json` 变成半截 JSON；下次启动读取失败，**用户的协议选择、串口参数、窗口布局全丢**。

**建议**：抽一个 `atomic_write_json(path, obj)`（写 `.tmp` → `os.replace`，失败保留旧文件），全项目替换。
新模块 `production_testbench_core.save_config` 已经是原子写，直接复用它的写法即可。
同时给 `config.json` 加 `schema_version` 与迁移钩子（串口工具已有局部迁移经验，见 CHANGELOG 1.23.49）。

**验收**：写入过程中强杀进程 20 次，`config.json` 始终可被 `json.load` 解析。

### 3）没有代码签名（推广第一道坎）

**现状**：103 MB 未签名 exe，Windows SmartScreen 会拦「未知发布者」，部分企业杀软直接隔离。
公众号/朋友圈带来的是**陌生用户**，这一步的流失率远高于功能问题。

**建议**：

- 短期：下载页显著位置给 **SHA-256 + 校验方法**（已有 hash 可自动生成）；
- 中期：买 OV 代码签名证书（约千元/年），给 exe 和安装包签名；EV 证书可立即建立 SmartScreen 信誉；
- 同时给安装包做**版本信息 + 版权信息**（spec 里已有 FileVersion，补 CompanyName/LegalCopyright）。

### 4）没有「一键诊断包」

**现状**：用户报「解析不对/连不上」，你要依次要：软件版本、协议、原始报文、配置、日志、系统版本。
远程支持的时间成本极高，也是公众号运营最容易被拖垮的环节。

**建议**：帮助菜单加「生成诊断包」，一键打包：

- `version.txt`（APP_VERSION / BUILD_DATE / Python / PySide6 / OS 版本）
- `config.json`（**脱敏**：去掉 API Key、串口端口可保留）
- 最近 N 条日志（各页面日志窗口的内容）
- 当前报文（可选、用户勾选）
输出一个 zip，用户直接发给你。**半天可完成，收益最大**。

## 三、P1：一个月内值得做的优化

### 性能

| 项 | 证据 | 做法 | 预期 |
|----|------|------|------|
| 拓扑页首开 1.59 s | `topology_graph` 顶层 `import networkx` 占 0.97 s；`TopologyWidget()` 本身只要 0.03 s | ① 把 `TopologyGraph` 改成**首次加载数据时才创建**（页面先出壳，导入放到后台线程）；② 中长期用自有树形布局替换通用图算法 | 首开 1.59 s → 0.2 s 级（只做①可去掉卡顿感） |
| 蓝牙页首开 0.6 s | `bleak/winrt` 导入 | 只在「扫描」时导入；页面先显示未连接态 | 首开 → 0.1 s |
| 单文件 EXE 启动解包 | 103 MB | 主推 **安装版（onedir）+ 便携版 zip**，单文件只做应急 | 冷启动预计 3.2 s → 1.2 s 级 |
| 批量导出内存 | 20k 帧完整字段表 ≈ +88 MB；100k 帧 ≈ 400 MB+ | 只保留摘要；详情按需重解析（`parse_one_frame` 已是唯一实现）；导出分批写 | 避免大日志 OOM |
| 生产测试架日志 | 每帧一次 `insertText` | 高吞吐时 100 ms 合并刷新 | 10 kbps 以上不卡 UI |

### 稳定性

1. **异常分级**：`except Exception` 1635 处、裸 `except:` 115 处、其中 395 处紧接 `pass`。
   不是都要改，但**协议解析、配置读写、升级**三条链路必须禁止「静默吞」：
   统一 `logger.warning(..., exc_info=True)` + 用户可见提示。建议先加 `-W error::DeprecationWarning`
   与「未捕获异常钩子」（`sys.excepthook` + `threading.excepthook`）写崩溃日志。
2. **串口订阅者互斥**：串口工具 / 蓝牙 / 生产测试架 / 监控器 / 光伏升级都订阅同一 `raw_data_received`。
   同时打开多个页面时，同一批字节会被多份解析（CPU 浪费，且语义上容易误判）。
   建议：给「谁在占用串口」一个显式状态，非当前页只保留原始字节缓存，不解析。
3. **线程登记核查**：现有 10 个 `QThread` 子类、24 处 `thread_registry.track`，建议加一条测试：
   枚举所有 QThread 子类，断言构造后已登记（避免退出时线程未回收导致进程残留）。
4. **长稳测试**：8 小时连续收包（每秒 10 帧）+ 反复切换页面，观察 RSS 与句柄数；目前没有这类测试。
5. **小 bug**：启动时日志里出现 `set_btn_icon 未知图标键: 'settings' / 'search'`（`gui_utils._STANDARD_ICON_MAP` 缺键），
   对应按钮会**静默没有图标**。补两个映射或改用已有键即可。

### 自动升级（在 P0 兜底之上）

- **增量更新**：103 MB 全量对现场网络不友好。可用「exe 差分（bsdiff/zstd patch）」把常见升级降到 5~10 MB；
  退一步也要支持**断点续传**（现在是大文件一次下载）。
- **灰度/通道**：`stable` / `beta` 两个通道，先给自己和小范围用户发 beta，再推 stable。
- **企业内网**：已有私有 HTTP 源，建议补「离线升级包」说明（U 盘拷贝 + 手动替换 + 校验）。
- **升级提示文案**：把「更新说明」里的破坏性变更（配置格式、协议行为）标红，避免用户升级后行为变化却不知道。

### 协议解析准确性（这是产品的命）

现状底子很好：15 协议、14 个 validator、190 个测试文件、桌面/Web 对拍。但还有三块可以更"产品级"：

1. **真实帧语料库**：建议建 `test/frames/<protocol>/*.hex`，每个协议至少 5 条**现场脱敏实帧**，
   测试做三件事：能解析、重建后逐字节相同、校验器全通过。新增协议/改公共代码时这是最有效的护栏。
2. **模糊测试（当前只有 1 个测试文件涉及随机）**：对每个 parser 灌随机字节/截断帧，断言「不崩、不卡死、给可读错误」。
   用固定 seed 跑 1 万次，CI 里 30 秒能跑完，能提前发现 `IndexError` / 死循环。
3. **错误信息分级**：现在多数失败只给「解析失败」。建议统一成三段式：
   `哪一层失败（链路/应用/A-XDR） → 期望什么 → 实际什么（hex + 偏移）`。
   这条直接决定用户能否自助排障，也是公众号文章最好的素材。
4. **协议版本/差异**：同一协议不同年份版本（如 698.45 2017 vs 2021 补遗）字段有差异，
   建议在协议下拉里显示版本，并在解析依据里注明「依据哪一版第几表」。

### 多协议能力的产品化

- 已有 `protocol_registry`（能力/别名/Tab/校验/提取/包装）是很好的抽象，建议再加两个字段：
  `maturity`（实验/稳定）、`since_version`，界面上标注「实验」标签，避免用户拿未稳定协议下结论。
- Web 版 12 协议 vs 桌面 15 协议：推广页必须明确「桌面端专属」，否则用户按 Web 预期下载会失望。
- 建议做一个「协议覆盖矩阵」页面（协议 × 解析/组帧/校验/升级/监控），既是文档也是卖点。

## 四、P2：季度级（决定能不能长期做大）

1. **表格虚拟化**：批量结果、查询页若用 `QTableWidget` 全量插入，几万行会明显卡；
   改 `QAbstractTableModel` + `QTableView`，10 万行也能流畅滚动。
2. **崩溃/异常上报（可选加入）**：默认关闭、首次启动询问，只上报版本/异常栈/协议，不上报文内容。
   没有它，你永远不知道用户那边崩在哪。
3. **配置与数据分离**：`config.json` 越来越大（窗口状态、主题、更新、LLM Key…），建议拆分并加密敏感项（DPAPI）。
4. **可访问性与高 DPI**：125%/150% 缩放下的几何回归（现有一部分），以及键盘全流程可用。
5. **性能预算进 CI**：把 `tools/perf_probe.py` 接进 CI，启动/内存/解析吞吐超过阈值就告警，防止慢慢劣化。
