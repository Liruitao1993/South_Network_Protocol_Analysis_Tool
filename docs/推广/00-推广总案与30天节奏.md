# 推广方案：从「没人知道」到「有人用、有人 star」

> 现状基线（2026-10-19）：6 star / 4 fork，近 14 天 **60 次访问、14 位独立访客**，最新版 exe 下载 14 次。
> 结论先说：**问题不是「东西不好」，是「几乎没人知道它存在」**，加上仓库门面有几处会劝退的硬伤（已修）。

---

## 一、先修门面，再谈推广（顺序不能反）

推广的本质是「把流量倒进一个能转化的页面」。门面没修好，投多少流量都是漏的。

| 已完成 | 为什么这件事影响 star |
| --- | --- |
| 5 张 README 截图中文全是方块（□） | 访客第一眼看到「□□□」，会直接判定项目是半成品并关掉页面。这是最贵的一处硬伤，已用真实界面重拍 |
| 没有 LICENSE 文件 | 徽章写 MIT，仓库却「无协议」→ 法务/公司环境无法采用，也不像正经开源项目。已补 |
| README 977 行 / 114 KB | 首屏看不到重点，手机端要滑很久；更新记录占了 1/3。已拆成 README + CHANGELOG + 两份 docs，README 现在 1 屏内讲清「是什么/给谁用/怎么装」 |
| 没有 Issue / PR 模板 | 开 issue 的人不知道要给什么信息，你会反复问「请提供报文」。已补表单，直接收敛到 hex + 协议号 + 标准条款 |
| 没有 CI | 绿勾是「项目活着」的社会证明。已加（核心测试 116 项 + 未定义名检查） |

### 还需要你亲手做（我做不了或需要你的账号）

   分享到微信/知乎/掘金时，卡片头图决定点击率。

## 二、先想清楚：谁会 star 一个电力报文工具

不要把「程序员」当受众。真正会 star / 会用的是这四类人，他们的信息源完全不同：

| 人群 | 他们在哪 | 他们关心什么 | 内容形态 |
| --- | --- | --- | --- |
| 电力/计量现场调试、运维 | 微信群、知乎搜索、CSDN、B站、公众号 | 「这个报文为什么不合格」「怎么快速定位」 | 案例复盘 + 动图 |
| 载波/双模模块厂商 FAE、测试工程师 | 行业群、厂商内部群、电子发烧友 | 协议一致性、台体联调、测试报告 | 对照表 + 实测截图 |
| 电科院/检测机构、标准编写参与者 | 知乎、知网圈、行业会议 | 标准解读的准确性、覆盖度 | 标准条款逐条对照 |
| 高校/职院电力信息通信方向师生 | B站、CSDN、Gitee、GitHub | 能不能跑起来、有没有源码可学 | 上手教程 + 源码导读 |

**切入点排序**（按「人最多 × 竞争最少」）：
1. 搜「698.45 报文解析」「DLT645 报文 解析 工具」「载波 报文 分析」的人 —— 搜索意图极强，几乎没有像样的中文工具内容。
2. 搜「DLMS 报文解析」的人 —— 有国际需求，但中文内容更少。
3. 电表/模块的**具体报错场景**（如「698.45 校验失败」「HCS 错误」）—— 长尾但转化最高。

## 三、内容主线：一个可复用的「爆款结构」

不要写「我做了个工具，求 star」。写**别人搜得到的问题**，工具只在解法的位置出现。

```
标题：{具体故障现象}，我用 5 分钟定位到了（附报文）
1. 现场现象：一段看不懂的 hex + 一个错误结论
2. 人肉排查有多痛：翻哪本标准、第几页、对哪几个字节
3. 拆解：这帧到底怎么读（逐字段表格截图）
4. 结论：为什么不合格（校验/长度/地址/时序）
5. 顺带说一句：这套流程我做成了工具，开源，链接
```

这个结构在知乎、CSDN、公众号都能直接用，只是标题和长度不同。

## 五、几个能显著抬高 star 的具体动作

1. **README 首屏放 GIF，不放静态图。** 静态图证明「有界面」，GIF 证明「真的能跑」。
2. **标题里带标准号。** 「698.45」「DL/T 645-2007」「IEC 62056」是精准关键词，搜的人少但意图极强。
3. **把「⚠ 未填充」这类反直觉设计写进 README。** 它在 FAQ 里，能减少 30% 的重复 issue，也让人相信作者懂现场。
4. **每条 issue 都在 48 小时内回。** 一个有人回的仓库和一个没人回的仓库，star 转化差好几倍。可以先回「收到，我复现一下，麻烦补一下 xx」。
5. **Release 说明要像人写的。** 目前 1.23.86 的说明是全量变更，建议首行写「一句话：这次解决什么现场问题」。
6. **不要刷 star。** 短期内会被识别，且破坏你在这个圈子里的信誉，得不偿失。
7. **在工具里留一个「Star」入口。** 仓库里已有 `test_about_github_star.py`，说明「关于」页应该已有入口 —— 确认它在**用户第一次成功解析之后**才出现，而不是启动就弹。

## 六、衡量：只看三个数

| 指标 | 现在 | 30 天目标 | 怎么看 |
| --- | --- | --- | --- |
| 独立访客（14 天） | 14 | 300+ | Insights → Traffic |
| Release 下载（单版本） | 14 | 100+ | Releases 页 |
| Star | 6 | 40+ | 仓库首页 |

> 说明：这是行业工具，不可能有通用开源项目的量级。40 star 已经意味着「在国内电力报文工具这个小池子里有人认识它」。
> 如果三个月后仍是个位数增长，真正的问题多半是**「目标人群根本不在 GitHub 上」** —— 那时应该把重心放到 Gitee、公众号和行业群，而不是继续优化 README。
