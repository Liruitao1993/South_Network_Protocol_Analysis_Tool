# 协议8/6 跳过前导 FE 唤醒字节（解析+校验+偏移）

## Goal

让本工具**按规范接受带前导 FE 的 68 家族链路帧**，覆盖单帧解析、串口工具/蓝牙工具解析回调、
快捷解析小窗、批量详情、以及**校验**路径；并让「蓝牙发送为何分包」这一现象在界面上自查自明。

这不是「容错放宽」，而是**规范符合性修复**：

- 协议8（DL/T 698.45-2017）§6.3.1 字节规则 b)：`协议文档/8.698.45协议/面向对象的用电信息数据交换协议(20210910).md:509`
  > b) 在有效数据帧前加 4 个 FEH 作为前导码；
- 协议6（DL/T 645-2007）§5.3.1 前导字节：`DLT645-2007.md:486`
  > 在主站发送帧信息之前，建议先发送 4 个字节 FEH，以唤醒接收方。

即：**规范规定 68 家族链路帧可以（698 是必须）带 FE 前导码**，本工具此前把首字节当起始符判据 →
带 FE 的合法帧一律报 `起始字符错误: 0xFE`。

## 报障事实（本任务证据基线）

### 报障 1：协议8 回包带 FE 前导，解析失败

用户现场（蓝牙工具页，日志 `[RX·0xFFE1]`，39 字节）：

```
FE FE FE FE 68 21 00 C3 05 11 11 11 11 11 11 00 84 84 85 01 01 40 01 02 00 01 09 06 11 11 11 11 11 11 00 00 5D A0 16
[解析·698.45协议] ❌ 解析失败 = - 起始字符错误: 0xFE, 期望 0x68
```

实测（已复现）：去掉 4 个 FE 后为 35 字节，`L=0x21=33` ⇒ 整帧 = `L + 2` 自洽，
HCS `84 84` 通过、FCS `A0 5D` 通过，可完整解出 GET-Response（OAD `40010200` = 通信地址，6 字节数据）。

### 报障 2：25 字节的发送也要分包

用户现场日志：

```
[TX] 68 17 00 43 05 AA AA AA AA AA AA 00 AA 2A 05 01 01 40 01 02 00 00 C6 07 16（25 字节）
[TX] 分包 1/2：68 17 00 43 05 AA AA AA AA AA AA 00 AA 2A 05 01 01 40 01 02   （20 字节）
[TX] 分包 2/2：00 00 C6 07 16                                                   （5 字节）
```

分包尺寸 20 字节 ⇒ BLE ATT 层 `MTU − 3 = 20`（协商 MTU = 23）。**应用层无法一次写出 25 字节**，
只能把「为什么分包 / 单包上限是多少」在界面与文档里说清楚（见 R6）。

## Requirements

### R1 前导 FE 的单一来源判定

- R1.1 新增纯逻辑模块 `wakeup_prefix.py`（零依赖、无 Qt、不 import 任何 parser）：
  `WAKEUP_BYTE = 0xFE`、`wakeup_prefix_len(data) -> int`、`strip_wakeup_prefix(data) -> (frame_bytes, skipped)`。
- R1.2 判定口径：**只跳过帧最前面的连续 `0xFE`**（0~N 个，N 不设上限，按实际字节数）；不跳过任何其它字节。
- R1.3 该判定**只对 68 家族链路帧（协议8、协议6）启用**；协议 0/7/9/10/11/12/13 行为一律不变（R5）。

### R2 协议8（DL/T 698.45）解析

- R2.1 `DLT69845Parser.parse` 在入口剥离前导 FE 后解析；`原始数据` 字段**保留用户原始输入**
  （含 FE，便于追溯），并在结果中记录 `唤醒前导`（字节数 + 原始值）。
- R2.2 `DLT69845Parser.parse_to_table` 在表格**首行**插入前导行
  `唤醒前导字节 / FE FE FE FE / - / <说明：规范 §6.3.1 b) 前导码，非帧内容，解析已跳过> / 0 / skip-1`，
  其后所有帧内行的 `byte_start/byte_end` **整体 +skip**。
- R2.3 无前导 FE 的帧，表格输出必须与改动前**逐行逐字节相同**（硬约束，回归锚点）。
- R2.4 FE 之后不是 `0x68`、或剥完后不足最短帧长时，仍按既有失败路径给出可读错误（不空白、不臆造）。

### R3 协议6（DL/T 645-2007）解析

- R3.1 `DLT645Parser.check_structure` / `parse` 在入口剥离前导 FE（`check_structure` 对已剥离输入幂等）。
- R3.2 `parse` 结果新增 `wakeup_len`；`raw_hex` 保留用户原始输入（含 FE）。
- R3.3 表格转换 `protocol_registry.DLT645GuiParser.parse_to_table` 在首行插入同款前导行，并把
  **全部行的偏移整体 +skip**（含 `数据长度`/`数据标识 DI`/`数据内容`/`数据域`/`校验和`/`帧结束符` 等按字段名匹配的分支）。
- R3.4 `valid` 语义不变（仍为「结构OK and 校验OK and 长度相符」）；虚拟表（`dlt645_sim`）行为不得改变。
- R3.5 无前导 FE 的帧，解析结果与表格输出与改动前**逐行相同**（硬约束）。

### R4 校验路径一致性（不得出现「解析成功但校验报起始符错误」）

- R4.1 `validator/dl_t698_45_validator.py`：先剥离前导 FE 再走全部检查（最小长度 / 起始字符 /
  长度域一致性 / HCS / FCS / 结束字符）；`skip > 0` 时追加一条 **PASS 说明项**（名称含「前导」，说明为「跳过 N 字节 FE 前导码」）。
- R4.2 `validator/dlt645_validator.py`：同上（最小长度 / 起始符1 / 起始符2 / 结束符 / CS / 数据长度）。
- R4.3 无 FE 的帧，校验输出项与结论必须与改动前一致。

### R5 范围与不回归

- R5.1 桌面、Web（`reflex_web`）两端行为一致（两端共用同一个解析器/校验器，不得在 Web 侧另写一份剥离逻辑）。
- R5.2 批量提取（`_extract_69845_frames` / Web `extract_69845_frames` / `batch_core`）已天然从 `68` 起同步，
  **不改**；但必须有测试钉住「带 FE 的混合日志仍能提取出正确帧」。
- R5.3 串口工具/蓝牙工具的**分帧策略表**（`STRATEGY_BY_PROTOCOL` / `frame_length_for`）不因本任务改变：
  带 FE 时不满足 `buf[0] == 0x68` ⇒ 走既有时间聚合，整段交给解析回调，由 R2/R3 的链路层容错兜住。
- R5.4 协议 0/7/9/10/11/12/13 对带 FE 输入的既有行为**不得变化**（新增护栏测试）。

### R6 蓝牙分包原因的可见性（回答报障 2；分包本身不可消除）

- R6.1 `bluetooth_worker._write_coro` 在分包写入（`len(chunks) > 1`）时输出一条说明性日志：
  单包上限（字节）、包数、协商 MTU 与来源（特征码免响应写上限 / MTU−3）。
- R6.2 `bluetooth_tool_widget` 的连接信息区已有「MTU：N 字节（单包上限 M）」，保持；
  分包原因说明**必须与 `chunk_size_for_mtu` 同一来源**（禁止在界面另算一份）。
- R6.3 文档侧记录三条硬事实：① ATT 层 `MTU − 3` 是物理上限，应用层无法一次写出 25 字节；
  ② 包间延迟默认 20 ms，而 698 §6.3.1 c)「数据链路层帧的字节之间无线路空闲间隔」⇒ 建议把包间延迟设为 0；
  ③ 减少分包只能靠设备端支持更大 ATT MTU。

## Scope 边界（明确不做）

- **不**把前导 FE 容忍扩展到协议 0/7/9/10/11/12/13（无规范依据；避免掩盖真实错帧）。
- **不**改串口/蓝牙的分帧策略表与时间聚合参数（R5.3）。
- **不**改虚拟表（`dlt645_sim` / `meter_sim`）行为、不改 `valid` 语义。
- **不**试图消除 BLE 分包（ATT 层物理限制），也**不**改「包间延迟」默认值
  （改默认值需配置迁移，见 AGENTS §8 陷阱 59；本任务只在文档给出建议）。
- **不**改协议13（依瓦定制645，另一个在途任务）的任何行为。

## 存疑 / 需在实现中确认

- **D1**：前导 FE 是否可能出现在**帧中间**（非前导）？规范只定义「帧前」。本任务只剥帧首连续 FE。
- **D2**：`0xFE` 是否可能成为某协议帧的**合法首字节**？对 68 家族：不可能（68 家族首字节恒 `68`）。
  对协议 9/10/11（FC 起头）已排除在范围外，不会误剥。
- **D3**：蓝牙「包间延迟」对 698 的影响程度取决于设备固件是否把每个 ATT 包立即转 UART —— 文档按
  「可能违反 §6.3.1 c)」如实提示，不宣称必然失败。
