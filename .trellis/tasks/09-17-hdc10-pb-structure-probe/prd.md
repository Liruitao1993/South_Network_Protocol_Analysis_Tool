# 协议11 PB 结构探测：物理块无 PBH 时回退直解 MAC 帧

## 背景与问题

现场报障（2026-09-17）：用户提供一条 **HDC 1.0 SOF 帧**（147 字节，来自现场设备/监控日志），
在 **协议10（国网新一代双模）** 下「自动识别」可完整解析出业务内容，在 **协议11（HDC 1.0）** 下
只输出 17 行（仅 FC 字段）后终止，用户看到的表现是「无法解析」。

现场帧（FC 16 字节）：

```
01 55 E2 D4 33 F0 FF 03 D3 13 B6 42 00 BE AF B8 | 10 00 FF 3F 02 68 62 30 3A 00 CF 08 00 ...
```

实测 FC 判定成立：`DT=1`（SOF 帧）、`标准版本号=0`（HDC 1.0）、
`FCCS(BE AF B8) == crc24(FC[0:13])` ✓。

### 根因（实测确认，非推测）

| 环节 | 协议10 | 协议11 |
| --- | --- | --- |
| FC 后定位 | `gw_new_gen_parser._locate_pbh_mac`：**内容驱动多形态探测**（形式1 `PBH+MAC` / 形式2 `MAC 无 PBH` / 形式3 直接应用层 / 形式4 `PBH+应用层`），配合应用层严格扫描（端口 + 报文ID + 控制字=0 + 业务头 `version=1` + 头长度 4~64） | `hdc10_parser._parse_pb_block`：**结构硬判** —— `pbh = data[16] = 0x10` → `bit6(帧起始)=0`、`bit7(帧结束)=0` → 落入 else「非帧起始PB」→ **输出 1 行 raw hex 即终止** |
| 该帧结果 | 54 行（MAC 头 + 应用层报文 + 业务字段） | 17 行（FC 14 行 + FCCS + 1 行 raw hex） |

该帧的物理块**未携带 PBH**。HDC 1.0 表37 / HDC 2.0 表21 均规定
`PB = PBH(1B) + PB体 + PBCS(3B)`，故这是实机/日志侧的变体形态；但它是**真实输入** ——
协议10 容忍它、协议11 直接放弃，**同一仓库两套策略不一致**，属真实缺陷。

### 证据链（可复现）

1. 按 `data[16]` 作 MAC 帧头解：标准帧协议（版本 0）、原始源TEI=`0x001`、原始目的TEI=`0xFFF`、
   MSDU 类型=`48`（应用层报文）、MSDU 长度=`58`、
   MAC 地址 `20:00:00:27:16:39` / `99:00:00:35:47:99`
2. **`ICV@102 = 0x552B1A7A` 与 `crc32(MSDU[44:102])` 完全相等** → 1/2³² 巧合不可能
3. 模拟修复 `_parse_mac_frame(data[16:], 16)` → **37 行完整解析**：端口 `0x11` 抄表业务、
   报文ID `0x0003` 终端主动并发抄表、规约类型 `3`（DL/T 698.45）、转发数据长度 `46`、
   ICV `✓ 校验正确`、帧尾 41 字节填充正确识别
4. 反证：按协议11 的 PBH 假设（PBH@16，MAC 头@17）解 → MSDU 长度 = **1792**（荒谬）

### 同类点（本任务范围内）

| 位置 | 现状 | 是否本次修 |
| --- | --- | --- |
| `hdc10_parser._parse_pb_block`（`:867`，else 分支 `:988`）→ 覆盖 `auto`/`fc_pb`/`pb_only` | 硬判，PBH 不合规即放弃 | ✅ 主目标 |
| `hdc10_parser._parse_pb_and_mac_header`（`:3026`）→ 覆盖 `fc_mac` | **无条件**把 `data[0]` 当 PBH（`mac_data = data[1:]`），PBH 缺失即整体错位 1 字节 | ✅ 同类，一并修 |
| `hdc10_parser._parse_mac_only`（`:3011`） | 已有探测：`data[0] & 0x80` → `hdr_start = 1` | 已具备，仅复核与统一 |
| `hdc10_parser._scan_all_pb`（`:999`） | 多 PB 边界按 PBH 序列号扫描 | 复核（多 PB 场景不得回归） |

## 需求

- **R1 不得直接放弃**：协议11 在物理块首字节不是合法 PBH 时，必须做形态探测并回退解析，
  输出完整内容并显式标注形态 —— 遵循既有原则：用户点了解析就必须看到内容 + 明确提示，不得空白
- **R2 探测必须内容驱动**：不能只看首字节位域（`0x10` 既可解释为「PBH：seq=16, 起始=0, 结束=0」，
  也可解释为「MAC 版本 0 + 源TEI 低 8 位」）；判据须包含 MAC 头合法性、MSDU 类型/长度自洽、
  应用层可定位性等**内容证据**
- **R3 与协议10 同源一致**：同一帧在协议10 / 协议11 下的 MAC 层与应用层关键字段必须一致，
  避免给用户两套互相矛盾的答案
- **R4 形态显式标注**：解析表格须标出本次采用的结构形态（含 PBH / 无 PBH）及判据，用户能自行判断
- **R5 既有行为不回归**：合法 PBH 帧（含 `test/hdc10_real_frames.pkl` 的 60 个真实 PB 帧）
  解析结果**逐行不变**
- **R6 入口一致**：`auto` / `fc_pb` / `fc_mac` / `pb_only` 四条经物理块解析的路径对该帧行为一致

## 非目标（避免范围蔓延，另行立项）

- **FC 可变区域解释差异**：协议10 按「TDA 下行帧」解 `FC[4:12]`、协议11 按 PLC SOF 帧参数解同一 8 字节
  （两协议对同一帧给出不同源/目的TEI 数值）—— 需独立核实规范后处理
- **抄表 DATA 内嵌协议展开**：本条帧 DATA 域内是 46 字节 698.45 报文，属已知缺口
- **MME 未实现的 7 类 MMTYPE**（代理变更 `0x0003/0x0004/0x0005`、过零NTB `0x000B/0x000C`、
  网络诊断 `0x004F`、无线信道冲突 `0x0080`）
- **无线(HRF)与 PLC 信道的 PB 尺寸/结构差异**：本次只做「有无 PBH」探测

## 验收标准

- **A1 现场帧可用**：用户帧在协议11「自动识别」下输出包含应用层报文段 —— 端口 `0x11`、
  报文ID `0x0003`、规约类型 `3`（DL/T 698.45）、转发数据长度 `46`，且 ICV 行显示「✓ 校验正确」
- **A2 双协议一致**：该帧在协议10 与协议11 下 MAC 层关键字段一致 ——
  原始源TEI=`0x001`、原始目的TEI=`0xFFF`、MSDU类型=`48`、MSDU长度=`58`、
  原始源MAC=`20:00:00:27:16:39`、原始目的MAC=`99:00:00:35:47:99`
- **A3 形态标注**：结果表中存在标明结构形态的行（无 PBH 时明确告知「未携带 PBH / 按无 PBH 形态解析」）
- **A4 无回归**：`test/hdc10_real_frames.pkl` 60 帧在 `pb_only` 下解析结果与改动前**逐行一致**
  （sha256 指纹对拍）；合法 PBH 完整帧解析逐行不变
- **A5 四入口一致**：`auto` / `fc_pb` / `fc_mac` / `pb_only` 对该帧均能给出内容，不得有入口放弃
- **A6 测试与发布自检**：新增 `test/test_hdc10_pb_structure_probe.py` 并登记 `release_check.py:CORE_TESTS`；
  `python release_check.py` 结果 `FAIL=0`
- **A7 变异反证**：把探测判据还原为「PBH 硬判」后，A1/A2/A5 相关断言**变红**（证明测试有约束力）

## 范围扩展（执行中确认纳入，回填）

1. **A2b 抄表头补齐字段**（同一现场帧暴露的第二类「无法识别」）：
   `_parse_meter_reading` 原先只输出到「报文序号」，缺字节6/7。现补齐：
   - 下行：字节6 设备超时时间（§5.3.1.8，×100ms）、字节7 选项字（§5.3.1.9 / 表8 / 表9）
   - 上行：字节6~7 选项字 16bit = 报文应答状态（第4-3部分 表10）；方向位 = 字节7 bit0
   - 现场帧实测：设备超时时间 2000ms、选项字 0x06（并发抄表 → 报文间间隔 60ms）
2. **协议依据表号核实（初版写错，已修正）**：PBH 为 **第4-2部分 表37**「物理块头的格式」
   （序列号 bit0~5 / 帧起始 bit6 / 帧结束 bit7，**无「块大小码」字段**），
   标准 MAC 帧头为 **第4-2部分 表10**；「表21 / 表11」是国网新一代（HDC 2.0）的表号，不适用于协议11。
3. **fc_mac 级别既有错位缺陷**（原属 A5，实测确认并修复）：`_parse_pb_and_mac_header`
   把原帧**绝对** `base_offset` 当成 `_parse_mac_header` 的 **data 内相对**索引（旧代码传 `base_offset+1`），
   使 fc_mac 下 MAC 头整体错位（原始源TEI 读成 2、MSDU类型 读成 0、MSDU长度 读成 1280）。

## 明确非目标（复核确认）

- **DATA 域内嵌 645/698.45 展开**：协议10 与协议11 **当前都没有**展开（两者一致），
  属新增功能而非本次「两端不一致」缺陷 → 另行立项
- MAC 头行的**偏移列**仍是「相对 MAC 帧切片」的 0~27（与 auto 一致），字段值不受影响
  → 不改，避免打破 60 帧基线
