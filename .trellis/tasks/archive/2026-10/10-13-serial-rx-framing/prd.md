# 串口工具：协议特征断帧支持前导 FE + 可调断帧字节超时

## Goal

让串口工具的**接收分帧**在两件事上可控、可解释：

1. 指定了协议时，**按该协议的结构特征断帧并拼接**（现状已有，但遇到**前导 FE** 会整体失效 → 一帧被切成多条 `[RX]`，见报障）；
2. **断帧的字节超时**可现场调整（现状是 4 个写死的模块常量，现场改不了）；
3. 未指定协议时，以**字节超时**为断帧依据（保留「68 结构自证即到齐成帧」的增强，用户 2026-10-13 选定）。

## 报障事实（证据基线见 `research/serial-framing-facts.md`）

现场（协议列 = `698.45协议`，接收模式 = 原始数据）一帧被切成两条 `[RX]`：

```
[RX] FE FE FE FE 68 21 00 C3 05 06 05 04 03 02                                  (14 B)
[RX] 01 00 EA 33 85 01 2C 40 01 02 00 01 09 06 01 02 03 04 05 06 00 00 1A 38 16   (25 B)
```

完整包 39 B = 4×FE 前导 + 35 B 的 698.45 链路帧（`L=0x0021` ⇒ 整帧 = `L + 2` = 35）。
实测：`frame_length_for("dlt698_45", 含 FE 首片) = 0`，**剥离 FE 后 = 35**（完全可判）。
根因：所有分帧函数一律要求 `buf[0] == 0x68` ⇒ 前导 FE 使其判不出 ⇒ `_frame_incomplete()` 也判 False
⇒ 该段不被当作「已开始未收全」⇒ 走 10 ms 静默窗口 ⇒ 首片单独成行。
这是 1.23.76（AGENTS §8 陷阱 75）**有意留下**的取舍：当时只保证「链路层能解析」，本次改为「分帧层也认前导」。

## Requirements

### R1 协议特征断帧：认前导 FE（68 家族）

- R1.1 `ft12_68`（协议 0/7）/ `dlt645`（协议 6）/ `dlt698_45`（协议 8）三种策略，以及**未指定协议**的
  68 启发式，先跳过帧首**连续** `0xFE`（复用 `wakeup_prefix.wakeup_prefix_len`，**不另写第二份扫描**）。
- R1.2 长度以「**含前导的总字节数**」返回 ⇒ 调用方 `buf[need-1] == 0x16` 的末字节自证语义不变；
  各策略内部的 645 双起始符 / 698 与南网国网互斥判定一律按**剥离后**的视图取下标。
- R1.3 缓冲里**只有前导 FE**（还没见到 `68`）视为「已开始但未收全」→ 继续等（受 R2 的等待上限约束）；
  确实是 FE 噪声时仍会在上限后按时间聚合刷出，**不丢数据**。
- R1.4 **只对 68 家族生效**：HDLC（`7EH` 定界）与 DLMS Wrapper（`00 01` 版本头）不加前导容忍
  （无规范依据；且它们首字节不是 `FE`）。
- R1.5 协议 1/5/9/10/11（无自证分帧依据）行为一律不变。

### R2 断帧字节超时可调（4 个参数）

- R2.1 UI 新增「断帧设置」：`字节静默超时` / `聚合最长持有` / `协议帧等待静默` / `协议帧等待上限`（毫秒）。
- R2.2 默认值 = 现行常量（`10` / `200` / `300` / `5000` ms）⇒ **老配置零行为变化**，
  因此只**新增键**，**不需要** `CONFIG_VERSION` 迁移（改默认值才需要，见 AGENTS §8 陷阱 49/59）。
- R2.3 持久化进 `serial_tool_config.json` 的 `params`；越界/非整数按范围夹紧并回落默认；
  读取对坏值宽容（沿用 `merge_params`）。
- R2.4 改值**即时生效**（不等 500 ms 去抖保存）；范围与语义写入 tooltip。

### R3 断帧方式

- R3.1 `auto`（默认）：**有协议** → 按协议结构特征断帧/拼帧；**无协议** → 字节超时聚合
  + 68 结构自证增强（到齐即出，不必等静默）。
- R3.2 `timeout_only`：忽略协议结构与启发式，**纯按字节超时**聚合（用户显式选择的兜底口径）。
- R3.3 落盘；切换时先刷出/清空缓冲，避免两种口径的数据混在一行（同 `_on_rx_mode_changed` 口径）。

### R4 可自查（现场能判断「此刻按什么在断帧」）

- R4.1 切换断帧方式 / 改动任一超时 → 输出一条 `[断帧] …` 说明行（走既有 `_log`，且随「显示发送/接收」开关与文件日志同源）。
- R4.2 每轮「开始发送」时输出一条断帧依据：当前协议 + 策略名 + 是否跳过前导 FE + 4 个超时值。
- R4.3 四个超时的 tooltip 必须说明「窗口作用 + 调大/调小的代价」。
- R4.4 **不得**为每次分帧刷屏（说明行只在设置变更/每轮开始时输出）。

### R5 不回归

- R5.1 **默认参数下，无 FE 输入的既有分帧行为逐字节不变**（硬约束；用既有测试与快照对拍）。
- R5.2 「按帧尾分割」模式完全不受影响（它走 `_frame_buffer` + 帧尾，不看策略）。
- R5.3 响应匹配仍按**累积接收缓冲**比对，语义与窗口不变；`SerialWorker` / `write_raw` 不改。
- R5.4 蓝牙工具、实时监控器、TCP 监控不在本次范围（蓝牙仍以静默超时切帧）。

## Scope 边界（明确不做）

- **不**改蓝牙工具的重组语义（仍静默超时切帧）、不改监控器 / TCP 监控的分帧。
- **不**给协议 1/5/9/10/11 新增「自证分帧依据」（没有规范依据，硬加会错切帧）。
- **不**改响应匹配的累积缓冲语义与窗口常量。
- **不**改 `SerialWorker`（端口/波特率归顶部串口配置）。
- **不**把断帧逻辑下沉到 worker 线程（AGENTS §8 陷阱 58 已记录的既有取舍）。

## 存疑 / 实现中确认

- **D1** 前导 FE 是否可能出现在**帧中间**（非前导）？规范只定义「帧前」。本实现只跳帧首连续 FE。
- **D2** 无协议时是否可能把「以 FE 开头的非 68 数据」长时间挂住？上限由「协议帧等待上限」（默认 5000 ms）
  兜底；纯 FE 无后续时，`_frame_incomplete` 会走等待分支但有上限 —— 实现时用测试钉住「最终一定刷出、不丢字节」。
- **D3** `timeout_only` 下 HDLC / Wrapper 是否也忽略结构？是（用户选择「仅按字节超时」即全局忽略结构）。
