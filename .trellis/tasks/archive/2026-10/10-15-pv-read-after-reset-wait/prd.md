# 光伏升级：不勾「传完后自动执行升级」也要读升级后版本；读前先等设备复位（默认 10 秒，可设）

## Goal

用户现场纠错（原文）：

> 「谁说不发送执行升级，就不读升级后版本？有的设备，只要发包完成自动复位升级，我是为了兼容此类产品，
> 做了发执行升级和不发执行升级的勾选，但是都应该读取后面的版本，由于设备复位升级需要等待一定的时间之后再去读，
> 默认等待10秒，不过可以手动设置」

⇒ 推翻上一任务「未发执行升级 ⇒ 不读升级后版本」的处理（那是我自作的主张，不是用户口径），并新增**等待设备复位**：

1. **「升级完成后读版本信息」与是否发执行升级命令解耦**：两种情形都要读 ——
   - 发执行升级（勾「传完后自动执行升级」）：执行升级**被确认后**读；
   - 不发执行升级：**最后一包写文件被确认后**读（该场景下设备往往收全包就自动复位升级）。
2. **读之前先等设备复位**：默认 **10 秒**，**可手动设置**（0 = 不等待、立即读）。

## Requirements

1. 新增参数「升级后等待(s)」：`spin_read_after_delay`，范围 `0..600`，默认 **10**，落盘（`read_after_delay_s`），
   与其它读版本输入一起在传输中被冻结。
2. 状态机新增阶段 `PHASE_WAIT_RESET`（状态仍是 `finishing`，故既有的「传输中」守卫/门控口径不变）：
   - 进入时机：① `PHASE_EXEC` 确认后（勾了自动执行）；② 最后一包 `PHASE_BLOCKS` 确认后（未勾自动执行）。
     两者都**仅当勾了「升级完成后读版本信息」**才进入等待；未勾则照旧直接收尾。
   - 等待用 **1 秒重复 QTimer** 倒计时：`_step_label()` 显示 `等待设备复位（剩余 N 秒）`（状态行可见），
     每秒刷新一次；倒计时归零 → 记一条日志 → 进入 `PHASE_VER_POST` 发读版本帧。
   - 等待时间 = 0 ⇒ **不发定时器、立即读**（日志写明「等待设为 0 秒」）。
   - 日志可查：进入时 `[信息] <原因>，等待设备复位升级：N 秒后再读版本信息（升级完成后）`；
     结束时 `[信息] 等待结束，开始读版本信息（升级完成后）`。
3. **等待期间不得卡死**：`中止` → `aborted` + 定时器停止 + 一个读版本帧都不发；`清除` → `idle` + 定时器停止；
   等待期间收到的帧**不当确认**（记 `忽略（等待设备复位中）`）；`cleanup()` 必须停该定时器。
4. **删除**上一任务的「未勾自动执行 ⇒ 不读升级后版本」分支与相应日志文案。
5. 收尾文案按情形区分（便于现场判读）：
   - 未发执行升级 + 读了后版本 ⇒ `文件传输完成（未发送执行升级命令，已读升级后版本信息）`；
   - 未发执行升级 + 未勾读后版本 ⇒ 仍是 `文件传输完成（未发送执行升级命令）`；
   - 发执行升级 + 读了后版本 ⇒ 仍是 `升级流程完成（已读升级后版本信息）`。

## Acceptance Criteria

- [ ] 「升级后等待(s)」spin：默认 10、范围 0~600、落盘并读回
- [ ] **未勾自动执行** + 勾读后版本：最后一包确认后 **0 帧新建**、phase=`wait_reset`、
      `lbl_status` 含 `等待设备复位（剩余 10 秒）`、日志含等待行；倒计时走完才发出**读版本帧**（OAD/PIID 正确）；
      其响应到达后 `done`/100%
- [ ] 等待 0 秒 ⇒ 不发定时器、立即读（日志写明）；`_reset_timer.isActive()` 为 False
- [ ] 勾了自动执行 + 勾读后版本：**执行升级确认后**才进入等待（顺序：exec 确认 → 等待 → 读版本）
- [ ] 等待中「中止」⇒ `aborted`、定时器停、零新帧；等待中「清除」⇒ `idle`、定时器停、零新帧
- [ ] 等待中收到帧 ⇒ 记 `忽略（等待设备复位中）`，不计确认、不影响倒计时
- [ ] 未勾读后版本 ⇒ 行为与改前**完全一致**（未勾自动执行时直接 `文件传输完成（未发送执行升级命令）`）
- [ ] `cleanup()` 后 `_reset_timer` 不再活跃；回归：`test_dl698_upgrade.py` 273 项 /
      `_gui.py`（原 276 + 新增） / `_tab_wiring.py` 29 项全绿 + `release_check` 无新增 FAIL

## Notes

- 为什么用 `finishing` 而不是新状态：`STATE_*` 是「在传输中」各项守卫（换文件/开始/清除/状态行）的唯一判据，
  新增状态要改 6 处；等待只是收尾阶段的**一个子步骤**，用 `PHASE_WAIT_RESET` 表达更贴合（且不动既有守卫）。
- 等待只在**读升级后版本之前**发生；升级前那次读版本没有等待。
- 现场依据（用户日志）：设备收满 255/255 包后回 `DAR=0 成功`，若不发执行升级命令，设备会自动复位升级 ⇒
  需要等它起来再读版本。
