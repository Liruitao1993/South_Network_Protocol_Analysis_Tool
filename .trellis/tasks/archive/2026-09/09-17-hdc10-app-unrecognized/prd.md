# HDC 1.0 应用层未识别内容收口

## Goal

协议11（HDC 1.0）的应用层报文在**无法识别**时不再静默丢内容：凡规范定义过的业务一律能被识别并给出可读结论，凡规范未定义格式的业务明确标注「格式未定义」，凡 MAC 头已声明为应用层的帧一律按应用层解析。

## Background

1.23.19 修复了协议11 app 级别抄表报文的 `NameError`（`proto_ver` 未定义）。顺着「同一份数据在不同解析级别下走完全不同的代码路径」排查同类缺陷，发现应用层解析存在 4 类结构性缺口（均为既有缺陷，非本次引入）：

**P0-1 / P0-2 — 规范定义过、代码零实现**
- `0x00A0 鉴权安全`（端口 `0x1A`）：`APP_PORTS`(hdc10_parser.py:136) 声明了端口名、`MSG_ID_NAMES`(:159) 声明了业务名，但 `_parse_app_payload`(:2051-2095) 的分派链**没有 0x0A0 分支**，且**没有任何分支判断 `port == 0x1A`**。
- `0x00A4 配电信息上报`（端口 `0x11`）：同上，有名字无分支。
- 现状：两者都落到 :2091 的 fallback，显示「未识别的业务数据(0x0A0)」+ 前 32 字节 hex。

**P1-3 — 端口白名单挡在通用头前面**
`_parse_app_only`(:2889) 与 `_parse_msdu_payload`(:1959) 硬编码 `data[0] in (0x11, 0x12, 0x1A)`。端口不在白名单时**连通用头（端口/报文ID/安全模式/控制字）都不解析**，直接判「未识别格式的应用层数据」。而 `_parse_application_layer` 本身对任意端口都有兜底（`APP_PORTS.get(port, f"保留(0x{port:02X})")`）——能力被白名单挡在门外，也违反 AGENTS.md 陷阱 23「字段声明与实际不一致时不得直接返回空白结果」。

**P1-4 — MSDU 分派无视 MAC 头已声明的类型（双向误判）**
MAC 头里有明确的类型字段，但 `_parse_msdu_payload`(:1931) 只把它用于 MME 判定（`msdu_type == 0`），应用层分支改看**首字节启发式**。实证（`test/hdc10_real_frames.pkl`，60 帧）：

| 帧 | MAC 头声明 | 实际结果 |
| --- | --- | --- |
| `msdu_type=48`（表10「应用层报文」） | 是应用层 | ❌ 未进入应用层解析，显示「类型48: 未定义(厂商扩展/待扩展)」 |
| `msdu_type=47`（不在表内） | 不是应用层 | ✅ 却进入了应用层解析（首字节恰好是白名单端口） |

**P1-5 — 安全模式报文仍按明文解析（比不解析更危险）**
`sec_mode`(:2010) 已被正确取出，但传给业务解析的是 `biz_id`，安全模式上下文丢失。规范 §5.2.3 定义报文ID最高4位为信道安全机制（如 `0x2004`=数据完整性保护的校时、`0x3032`=数据全面保护的传输文件数据）；此类报文数据域受保护，代码仍逐字段按明文解析并输出**看似正常的错误数值**。

## Requirements

- R1 规范定义过的业务不得显示为「未识别的业务数据」；无格式定义时须显式注明依据。
- R2 应用层通用头（端口/报文ID/安全模式/控制字）应能在任意端口下解析，不得由端口值决定是否解析。
- R3 「是否应用层」的判据以 MAC 头类型字段为准（表10 标准头 `48`、表13 单跳头 `128`），首字节启发式仅作无头上下文时的回退。
- R4 `sec_mode != 0` 时须给出醒目提示，说明数据域受保护、字段可能无效。
- R5 判据与类型值域只留一处常量定义（单一来源），不得在两个入口各写一份。
- R6 已知业务的现有解析输出不得改变（含字段值、行序、偏移高亮）。
- R7 桌面与 Web 两端摘要规则保持一致（陷阱 44 的 `_gw_app_biz_summary` 两份实现对拍）。
- R8 新增逻辑不得引入跨帧可变实例状态（陷阱 41）。

## Scope

### In Scope
- `hdc10_parser.py`：`_parse_msdu_payload` / `_parse_app_only` / `_parse_app_payload` / `_parse_application_layer` 的分派与呈现。
- 类型值域常量统一（标准头 48 / 单跳头 128；IPv4 49 / 129）。
- `sec_mode != 0` 的提示行及其对摘要的影响（必要时扩元数据黑名单，两端同步）。
- 新增回归测试套件并登记 `release_check.py:CORE_TESTS`。

### Out of Scope（另行立项，本次不做）
- 抄表 DATA 域内嵌 645 / 698.45 报文的展开（需接入 `dlt645_parser` / `dl_t698_45_parser`，属独立工程）。
- `hdc10_mme_parser` 未实现的 7 类 MMTYPE（`0x0003/0x0004/0x0005` 代理变更、`0x000B/0x000C` 过零NTB、`0x004F` 网络诊断、`0x0080` 无线信道冲突）。
- `0x00A0` / `0x00A4` 的**字段级**解析：已核实整套 HDC 文档（第1/4-1/4-2/4-3部分）中 `鉴权安全`、`配电信息上报` 仅出现在报文ID表与优先级表，**无任何字段格式定义** → 按 AGENTS.md「协议定义优先，禁止凭记忆推断」，本次只做到「识别 + 报名字 + 注明格式未定义」。
- IPv4 载荷（`49`/`129`）的深度解析，本次仅给明确提示。
- `_parse_msdu_payload` 中 MME 分支的 `except Exception` 静默吞异常（属 P2，本次不动）。

## Acceptance Criteria

- [ ] A1 端口 `0x1A` + 业务ID `0x0A0` 的报文：表格出现业务名「鉴权安全」与「格式未定义」说明；**不再**出现「未识别的业务数据(0x0A0)」。
- [ ] A2 端口 `0x11` + 业务ID `0x0A4`：出现「配电信息上报」+「格式未定义」。
- [ ] A3 端口 `0x13`（既有白名单之外）的合法应用层报文：通用头完整（端口行显示「保留(0x13)」+ 报文ID + 安全模式 + 控制字），而非整段「未识别格式」。
- [ ] A4 `msdu_type=48` 且端口非白名单的 MAC 帧：进入应用层解析（表内出现「── 应用层报文 ──」）。
- [ ] A5 `msdu_type=None` 且首字节非白名单：**保持现状**不判为应用层（回退路径不被放宽）。
- [ ] A6 `_parse_app_only` 收到完整 MPDU（非应用层）：仍走 FC 检测路径，行为不回归。
- [ ] A7 `sec_mode=2`（如 `0x2004` 校时）：出现「⚠ 安全保护」提示行；且校时字段解析结果与改动前**逐行一致**。
- [ ] A8 真实帧回归：`test/hdc10_real_frames.pkl` 全部 60 帧解析不抛异常；`msdu_type=48` 的帧进入应用层解析。
- [ ] A9 Fuzz：`MSG_ID_NAMES` 全部 24 个业务ID × 3 端口 × 长度 0~12（936 组合），另加 78 组表外ID，仍零崩溃。
- [ ] A10 摘要不退化：`test/test_gw_app_summary_detail.py`（42 项）通过；新增提示行不挤占关键业务字段位。
- [ ] A11 `release_check.py` FAIL=0 / WARN=0；`--sync-iss` 通过；版本号、CHANGELOG、README 徽章、两个 `.iss` 对齐。
- [ ] A12 变异反证：移除 `APP_MSDU_TYPES` 分派 → A4 变红；恢复端口白名单否决 → A3 变红；移除安全模式提示 → A7 变红。
