# EB 645 生成器口径修正为标准 DL/T645-2007

## Goal

修正「EB 数据标识 645 帧生成器」与国网内嵌 645 解析路径的加扰/校验和口径，使其与真实设备报文一致：数据域逐字节 +0x33、CS 覆盖帧头（`68 A0..A5 68 C L DATA`）。生成侧与解析侧必须同时修，否则两边口径不一致会让 EB 深度解析彻底失效。

用户价值：现状下本工具生成的 EB 645 帧发给真实 CCO/STA 会因 CS 错误被丢弃；而真实设备上报的加扰 EB 帧，本工具又解析不出内容（`_try_parse_embedded_eb` 按明文判 `EB` 直接 return False）。修正后「造得出、发得通、解得开」三者同时成立。

## Background（已确认事实）

完整证据链见 `research/cs-and-scramble-evidence.md`。要点：

- **真实抓包实证（决定性）**：`CCO-2-COM3-260628-124120 - 复制.log`（33.7 MB CCO 串口实测）中 3 帧独立内层 645 帧全部验证「CS = `sum(帧头…数据域末) & 0xFF`」且「数据域为 +0x33 加扰」：
  - L114491 `6833000000000068110433333433E516` → CS `E5` 吻合，DATA `33 33 34 33` −0x33 = `00 00 01 00`（DI 00010000 当前正向有功总电能）
  - L114504 `…689108333334333333333335 16` → CS `35` 吻合，还原为 DI + 值 0.00 kWh
  - L270631 `68251288060000681104333334337716` → CS `77` 吻合
  - 地址域**不加扰**（裸 BCD，低字节在前）
- **文档口径**：`协议文档/7.国网本地接口协议/附件1_v342.md` 附录3 L1526-L1528 明写各控制码「格式同 DL/T645-2007」，L1530 兜底「本协议未说明的部分按 DL/T645-2007 协议执行」；附件1 全文未对 CS 范围或加扰作例外规定。L241-L259 表格「645示例」列的 `EB030002`/`00H` 是**逻辑值展示而非线上字节**（同表「698格式示例」列才是真实字节串，698 不加扰）
- **生成侧缺陷（两处副本）**：`frame_gen_widget.py:961-975` `_build_eb_645_frame()` 与 `reflex_web/reflex_web/reflex_web.py:1550-1598` `gen_eb_645_frame()` 均为 `cs = sum(body) & 0xFF`（`body` 只含 `C+L+DI+DATA`，**漏掉帧头 8 字节**）且 `di_bytes`/`data` **未 +0x33**
- **解析侧缺陷（同根因另一半）**：`gdw10376_parser.py:2223-2254` `_try_parse_embedded_eb()` 直接用明文判 `data_slice[0] != 0xEB`（L2242），全文件检索 `0x33` **零命中**，且不校验内层 CS → 真实加扰 EB 帧（线上 `1E 36 33 35`）会被直接拒绝
- **自证循环**：生成侧不加扰 + 解析侧不还原，两边口径一致，故 `test_gdw_fujian.py` / `test_web_frame_gen_utils.py` 全过，但都与真实设备不符
- **仓库内已有正确参照**：`archive_widget.py:849-864` `_build_dlt645_read_energy_frame()`（+0x33 且 CS 覆盖全帧头）、`test/test_dlt645_lme.py:31-36` `build_frame()`
- **698 分支不受影响**：698.45 **不加扰**，口径本就不同；但 `reflex_web.py:1556-1557` 中 `gen_eb_645_frame()` 在 `gen_eb_format == "698"` 时转调 `_gen_eb_698_frame()`，函数名与职责不一致，修正时须避免误改 698 路径

## Requirements

- **R1** 生成侧改为标准口径：数据域（DI + 数据）逐字节 `+0x33`；CS = `sum(68H + A0..A5 + 68H + C + L + 加扰后数据域) & 0xFF`；地址域保持裸 BCD、低字节在前
- **R2** GUI（`_build_eb_645_frame`）与 Web（`gen_eb_645_frame`）**两处必须同步修改**，同输入产出逐字节一致
- **R3** 解析侧 `_try_parse_embedded_eb` 增加 −0x33 还原，并采用**双口径兼容**（见已决事项）；还原后的 DI 与数据内容再交给 `_parse_eb_di`
- **R4** 不得改动 698 分支行为（698 不加扰）；`gen_eb_645_frame` 转调 `_gen_eb_698_frame` 的路径必须保持原语义
- **R5** 按新口径重算并更新既有测试期望值，禁止手填 hex——期望值须由代码计算后写入断言
- **R6** 真实抓包回归：用 `research` 中记录的 3 帧真实内层 645 帧作为断言样本，确保解析侧能正确还原 DI 与 CS 校验通过

### 实施结果（口径最终结论，含对原 PRD 的修正）

- **DI 字节序最终定为「低字节在前」**：原 PRD/研究只证实了加扰与 CS 范围，未证实 EB DI 的线上字节序。实施中发现旧生成器与旧内嵌解析器都用**书写序（EB 在首字节）**，而真实抓包（DI `00010000` → 线上 `00 00 01 00`）证明标准 645 是**低字节在前**，且附件1 明写 645 承载「格式同 DL/T645-2007」。故生成器改走 `encode_di`（低字节在前）。
- **解析侧对 DI 字节序也做双口径兼容**：`data[3]==0xEB` → 低字节在前（标准，优先）；`data[0]==0xEB` → 高字节在前（旧口径回退），并在解析表格标注「DI 低字节在前（标准）/高字节在前（旧口径）」，避免万一有设备按旧序发送时整帧不可读。
- 解析表格新增三行标注（仅提示不阻断）：数据域口径（加扰）、DI 字节序、校验和 CS（正确/不符+期望值）。

## 已决事项

- **解析口径采用双口径兼容（用户 2026-09-07 确认）**：先按加扰还原判定（`data[0] == 0x1E` 且还原后为 `EB` 开头），失败则回退按明文判定，并在解析表格标注「明文未加扰（可能为旧版工具生成或部分固件实现）」。理由：① 存量明文 EB 帧散落在 `GW_command.json` 预设、`test_plan.json` 测试方案、服务端 `frameshare.db` 分享报文中，严格标准会全部失配；② **本仓库没有任何一帧真实的 EB 内嵌报文**（33.7 MB 抓包中只有标准 DI 内嵌帧），而附件1 文档表格字面写明文 `EB030002`，不能排除某些 CCO 固件照文档字面发明文；双口径对此免疫，成本仅一个 `if` 回退。放弃「严格标准」（存量数据失配 + 无容错）与「严格标准 + 迁移脚本」（服务端 `frameshare.db` 与他人数据覆盖不到）
