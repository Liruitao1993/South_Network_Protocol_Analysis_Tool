# 设计：应用层报文摘要的业务名与关键业务字段提取

## 1. 现状与缺口

```
桌面：_get_summary_from_table_data(main_gui.py:7977, proto in (10,11))
        └─ _get_gw_new_gen_summary(main_gui.py:8448)
             ├─ 物理层/网络层段：NID / 定界符类型 / MMTYPE / TEI / msduSeq / 发送类型 / MSDU类型
             └─ 应用层段：val("报文端口号") + val("报文ID")  ← 只这两段，无业务名、无业务字段
Web： web_utils.get_frame_summary(:845)
        ├─ proto in (9,10) → get_csg_new_gen_summary   ← 协议10 误用协议9（陷阱 31 既有漂移）
        └─ proto == 11     → get_hdc10_summary(:777)   ← 独立实现，应用层段取 comment 整句
```

协议11 应用层表的业务名在业务数据区头行、业务字段在其下；协议10 业务名已在「报文ID」解析值里、业务字段与元数据平铺——**必须用一条兼容两协议的规则**（见 prd 实测表结构）。

## 2. 设计决策

### D1 单一提取规则：`_gw_app_biz_summary(table_data) -> (业务名, [关键字段…])`

模块级**纯函数**（不依赖 Qt、不读全局状态），桌面与 Web 各放一份同名实现，靠对拍测试约束一致（两端暂不共享模块，见 prd Out of Scope / `09-15-web-shared-parse-core`）。

```python
# 应用层报文摘要的元数据字段（非业务语义，不占关键字段位）
_GW_APP_META_FIELDS = (
    "报文端口号", "报文ID", "安全模式", "安全机制", "业务报文ID", "报文控制字",
    "协议版本号", "报文头长度", "控制/保留", "数据长度", "报文序号",
    "转发数据规约类型", "规约类型", "发送类型", "MSDU类型",
)
_GW_APP_SUMMARY_KEY_FIELDS = 2   # 关键业务字段个数（prd 用户选定 2；常量便于调整）


def _gw_app_biz_summary(table_data) -> tuple:
    """返回 (业务名, ["字段名:解析值", ...])，最多 _GW_APP_SUMMARY_KEY_FIELDS 个。"""
```

**业务名（两协议兼容，按优先级）**：

| 优先级 | 规则 | 命中场景 |
| --- | --- | --- |
| 1 | 找到以 `── 业务数据` 开头的分隔行 → 取其后**第一个**「字段名有前导空格、解析值非空、非 `❌`/`⚠`」行的字段名（`.strip()`） | 协议11（`  开始升级`） |
| 2 | 否则取「报文ID」解析值（`item[2]`）——**仅当它不是 hex 形式**（不匹配 `0x…`/纯十六进制）时视为业务名 | 协议10（`开始升级`） |
| — | 都不命中 → 业务名为 `""`（摘要退化为现状，不报错） | 未知/保留业务 |

**关键业务字段**：按表内出现顺序遍历，取满足全部条件的行，直到收集到 `_GW_APP_SUMMARY_KEY_FIELDS` 个：

1. 字段名有前导空格（`name != name.lstrip()`，即子字段/业务字段层）；
2. `name.strip()` **不在** `_GW_APP_META_FIELDS`（精确相等或前缀匹配，兼容 `控制/保留` 这类写法）；
3. 不是 `── … ──` 分隔行、不是业务名行本身；
4. 解析值（`item[2]`）非空；
5. 解析值**不是字节数占位符**（`^\d+字节$`）——协议11 的业务名行与「数据长度」行属于此类，避免把区头当字段；
6. 输出 `f"{name.strip()}:{parsed}"`。

**实测预期**：
- 协议11 → 业务名 `开始升级`，字段 `升级ID:2075013183`、`升级时间窗:120分钟`
- 协议10 → 业务名 `开始升级`（走优先级 2），字段 `升级ID:2075013183`、`升级时间窗:120分钟`

### D2 拼接位置与去重（桌面 `_get_gw_new_gen_summary`）

在应用层段的 `报文:{msg_id}` 之后、`报文序号`/`规约`/`数据长度` 之前插入：

```python
biz_name, biz_fields = _gw_app_biz_summary(table_data)
if biz_name and biz_name not in {msg_id_value, ...已有段落文本}:
    parts.append(biz_name)              # 业务名单独成段（不带值）
parts.extend(biz_fields)                # 关键字段各成一段
```

- **去重规则**：业务名已作为 `报文:{msg_id}` 的显示值出现（协议10 的 `报文:开始升级`）时**不再单独追加**，避免 `报文:开始升级 | 开始升级`。
- **段落顺序**（最终形态）：
  - 协议11：`端口:18 | 报文:0x0030 | 开始升级 | 升级ID:2075013183 | 升级时间窗:120分钟`
  - 协议10：`端口:升级业务 | 报文:开始升级(下行) | 升级ID:2075013183 | 升级时间窗:120分钟`

### D3 不回归的既有段落

物理层/网络层段（NID / 定界符类型 / 帧类型 / MMTYPE / 源→目的TEI / msduSeq / 发送类型 / MSDU类型 / 测试模式）与失败帧分支**一行不改**；只在其后追加业务段（仅当存在业务数据区/应用层报文时才会命中，物理层帧不受影响）。

### D4 Web 同步：`get_hdc10_summary` 复刻 + 协议10 分派修正

1. `web_utils.get_hdc10_summary` 的**应用层段**按桌面 `_get_gw_new_gen_summary` 的应用层段逐段复刻（同一取值口径）：
   - `端口:` 取**解析值**（原实现取 comment，会得到 `端口:升级业务`，与桌面 `端口:18` 不一致）；
   - `报文:{解析值}` + 方向（方向从「应用层报文」行 comment 里取 `下行`/`上行`，与桌面同逻辑）；
   - 业务名 + 2 个关键字段（`_gw_app_biz_summary` 同规则、同黑名单、同常量）；
   - `报文序号`/`规约`/`数据长度` 与桌面同文案同顺序。
2. `get_frame_summary`：`if protocol_index in (9, 10)` → **只保留 9**；`10` 与 `11` 一并走 `get_hdc10_summary`（该函数已按 D1 兼容两协议）。这同时修掉陷阱 31 的既有漂移。
3. Web 的物理层/MSDU/MME 段**保持现有实现不动**（不在本任务对拍范围，差异属共享核心任务）。

### D5 对拍范围（边界明确，避免假红）

对拍断言**只覆盖应用层报文表**（本任务改动范围）：

- 输入：同一批 app 级别解析表（协议11 现场帧、协议10 同帧、以及 0x030 之外的 1~2 个业务帧若可得）；
- 断言：桌面 `_get_gw_new_gen_summary` 与 `web_utils.get_hdc10_summary` 输出**逐字符相等**；
- **不**对物理层/MME 帧做对拍（两端文案差异属既有，另案）。

## 3. 接口契约

| 位置 | 改动前 | 改动后 |
| --- | --- | --- |
| `main_gui`（模块级） | — | 新增 `_GW_APP_META_FIELDS` / `_GW_APP_SUMMARY_KEY_FIELDS` / `_gw_app_biz_summary(table_data)` |
| `MainWindow._get_gw_new_gen_summary` | 应用层段只有 端口/报文ID/序号/规约/长度 | 追加业务名与 ≤2 个关键业务字段（去重、顺序见 D2） |
| `web_utils.get_hdc10_summary` | 应用层段取 comment 整句 | 应用层段与桌面同口径 + 业务段；物理层/MSDU/MME 段不变 |
| `web_utils.get_frame_summary` | `proto in (9, 10)` → 协议9 摘要函数 | `proto == 9` → 协议9；`proto in (10, 11)` → `get_hdc10_summary` |

**兼容性**：网络层/物理层摘要与失败帧摘要**输出不变**；应用层摘要**变长**（既有测试若整串断言应用层摘要会需要同步更新——实施时按 `test_gw_monitor_summary.py` 的实际断言逐条核对，不静默改期望值）。

## 4. 验证策略

| 层级 | 手段 | 判据 |
| --- | --- | --- |
| 纯函数 | 直接调 `_gw_app_biz_summary`（构造最小表） | 协议11/协议10 两种布局都得到 `("开始升级", ["升级ID:…","升级时间窗:…"])`；元数据不入选；未知业务回落空 |
| 端到端摘要 | `_get_gw_new_gen_summary` + `web_utils.get_hdc10_summary` | 现场帧 → prd 验收 1/3 的精确文案 |
| 可区分性 | 用户 20 行样本批量解析（协议11，app 级别） | 20 条摘要**互不相同**且分钟数正确递减（验收 2） |
| 回归 | `_get_gw_new_gen_summary` 对网络层/测试模式表 | 与改动前逐字符一致（先取基线再断言） |
| 两端对拍 | 桌面 vs Web（应用层表 × 协议10/11） | 逐字符相等（验收 5） |
| 分派修正 | `web_utils.get_frame_summary(table, 10)` | ≠ `get_csg_new_gen_summary(table)`，且 == `get_hdc10_summary(table)` |
| 变异反证 | `_GW_APP_SUMMARY_KEY_FIELDS = 0` / 跳过业务名提取 | 验收 1/2/3 对应断言变红 |
| 发布自检 | `python release_check.py` | FAIL=0 / WARN=0 |

## 5. 回滚

改动集中在 `main_gui.py`（一个模块级函数 + 摘要函数内一个插入点）、`reflex_web/reflex_web/web_utils.py`（一个函数重构 + 一行分派）、1 个新测试文件、文档/版本号。无数据迁移、无持久化格式变化，`git revert` 即回滚。

## 6. 已知残余风险

- 「关键字段前 2 个」对某些业务可能不是最有信息量的两个（如分相数据的 A/B/C 相）——按用户选择固定 2 个，常量可调；若需按业务定制，另开任务。
- Web 与桌面仍是两份实现（本任务只保证规则与对拍一致）；根治见 `09-15-web-shared-parse-core`。
- Web 应用层摘要文案会**变短且更规整**（`端口:升级业务`→`端口:18`、去掉 comment 整句）——属与桌面对齐的改进，需在 CHANGELOG 明确记录为行为变更。
