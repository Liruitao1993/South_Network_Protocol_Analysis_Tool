# 协议10/11 应用层报文批量摘要显示业务功能与关键业务字段

## Goal

批量解析把解析级别选为「应用层报文(app)」时，摘要列现在只有 `端口:18 | 报文:0x0030`——同一批 21 帧**摘要完全相同**，扫读时无法区分业务功能与关键参数（用户现场反馈）。本任务让摘要带上**业务功能名**（如 `开始升级`）与**2 个关键业务字段**（如 `升级ID:2075013183 | 升级时间窗:120分钟`，正是这批帧的差异所在），桌面与 Reflex Web 两端同步，覆盖协议10（国网新一代）与协议11（HDC 1.0）。

## Confirmed Facts（代码与实测证据）

**协议10（国网新一代，同一帧，14 行）**：无「业务数据」区头；`  报文ID` 的**解析值已是业务名** `开始升级`；业务字段（`  升级ID`/`  升级时间窗`/`  升级块大小`/`  升级文件大小`/`  文件CRC校验`）与报文元数据**平铺在同一缩进层**（另有 `协议版本号`/`报文头长度`/`控制/保留`/`数据长度` 等元数据行）。

- 用户选定范围：**协议10 + 11**、**桌面 + Web 同步**；详细程度：**业务名 + 2 个关键业务字段**。

## Requirements

### R1 业务名提取（两协议兼容，单一规则）

- 协议11：存在 `── 业务数据 ──` 区头时，取其后第一个非空普通行的**字段名（去前导空格）**作为业务名（如 `开始升级`）。
- 协议10：无区头时，若「报文ID」的解析值不是 hex（非 `0x…` 形式）则视为业务名（如 `开始升级`）。
- 业务名**已出现在其它摘要段中时不重复追加**（协议10 的 `报文:开始升级` 场景）。

### R2 关键业务字段（业务名 + 2 个）

- 从「带前导空格的字段行」中按出现顺序取前 **2** 个，排除：
  - 元数据字段（两协议并集）：`报文端口号` / `报文ID` / `安全模式` / `安全机制` / `业务报文ID` / `报文控制字` / `协议版本号` / `报文头长度` / `控制/保留` / `数据长度` / `报文序号` / `转发数据规约类型` / `规约类型` / `发送类型` / `MSDU类型`；
  - `── … ──` 分隔行、业务名行自身、`❌`/`⚠` 行、解析值为空的行。
- 输出格式 `字段名:解析值`；字段数量为**模块级常量**（默认 2，便于按需调整）。
- 协议11 预期：`开始升级 | 升级ID:2075013183 | 升级时间窗:120分钟`
- 协议10 预期：`… | 报文:开始升级(下行) | 升级ID:2075013183 | 升级时间窗:120分钟`

### R3 不回归既有摘要能力

- 物理层/网络层摘要（NID / 定界符类型 / 信标类型 / MMTYPE / 源→目的TEI / msduSeq / 发送类型 / MSDU类型）与「测试模式」段落**逐字符不变**（协议9 摘要不在本任务范围）。
- 失败帧（`❌`）摘要仍返回失败原因。

### R4 Web 端同步（含协议10 分派修正）

- `web_utils` 侧实现**同一规则**（同一业务名/字段提取逻辑与同一元数据黑名单），并保持与桌面输出的段落顺序一致。
- 修正 `get_frame_summary` 的协议10 分派：协议10 不再走协议9 摘要函数，改用与协议11 同一实现（否则 R1/R2 在 Web 的协议10 上落空）。
- 测试中加**两端对拍断言**（同一样本帧 × 协议10/11 → 桌面与 Web 摘要逐字符相等）防漂移。

## Acceptance Criteria

1. 协议11 app 级别，现场帧摘要为 `端口:18 | 报文:0x0030 | 开始升级 | 升级ID:2075013183 | 升级时间窗:120分钟`（段落顺序与文案按设计）。
2. 用户 20 行样本批量解析后，摘要列**逐行可区分**（升级时间窗分别为 120/119/112/…/89 分钟）。
3. 协议10 app 级别同一帧摘要含业务名与 2 个业务字段，业务名不重复。
4. 网络层/物理层/测试模式摘要与改动前逐字符一致（回归断言钉住）。
5. 桌面与 Web 摘要对拍一致（协议10/11）；Web 协议10 不再走协议9 摘要函数。
6. `test/test_gw_app_summary_detail.py` 全绿；既有协议10/11 相关测试（`test_gw_monitor_summary.py`、`test_gw_batch_parse.py`、`test_gw_new_gen.py`、`test_hdc10.py`、`test_gw_parse_levels.py`、`test_web_parse_fixes.py`、`test_gui_batch_perf.py`、`test_csg_summary.py`）全绿；`release_check.py` FAIL=0 / WARN=0。
7. 变异反证：把关键字段数量改为 0（或在提取里跳过业务名）→ 对应断言必须变红（证明测试有效）。

## Out of Scope

- 协议9（南网新一代）摘要内容（`_get_csg_new_gen_summary` / `web_utils.get_csg_new_gen_summary`）不改——用户未提出，且其表结构/业务命名体系不同。
- 监控器实时列表摘要（`_get_monitor_summary`）不改（它复用同一函数，行为会随摘要增强自然变化，但不为其单独设计）。
- 详情面板/导出内容不变（详情本就有全部字段）。
- Web 批量对齐的其它项（摘要同源、跨行 payload、行号、导出字段）仍属 `09-15-web-batch-alignment`，本任务**只**动摘要字段提取与协议10 分派这一处。
- 不为每个业务类型硬编码字段名（如「0x030 → 升级ID/时间窗」）——统一规则即可满足，避免维护成本（YAGNI）。

## Risks / Deferred

- 统一规则对「业务名行」的识别：协议11 依赖 `── 业务数据 ──` 区头；若未来某业务表无该区头，则业务名回落到「报文ID 解析值非 hex」路径，两者都失败时摘要退化为现状（不报错、不空）。
- 关键字段固定取「前 2 个」：某些业务的关键参数可能不在前 2（如分相数据）；本任务按用户选择固定 2 个，常量可调；若后续需要按业务定制，另开任务。
- Web 与桌面摘要实现仍为两份（本任务只保证规则与对拍一致），根治属 `09-15-web-shared-parse-core`。
